# PROCESS IN — GitHub Product Showcase Standard v1

**Canonical visual and editorial standard for every public PROCESS IN product showcase.**

Reference quality: [Validate](https://github.com/stambolce/validate-survey-platform). Every product must look like a polished branded product presentation, not a generic software repository.

## Visual signature

- Official product logo first, centered and prominent. Never invent or replace an official logo. If the logo asset is not available, leave an explicit logo placeholder in the implementation plan and request the real asset.
- Bespoke wide SVG hero, designed for the **specific product**, with credible UI-style product illustration, compelling headline and intentional visual hierarchy. Do not recycle generic browser/phone mockups.
- PROCESS IN visual identity: restrained black/navy, blue and white, generous whitespace, subtle cool gradients, high contrast. No neon, purple, pink or arbitrary accent colors.
- Inter-first typography within SVG; GitHub README body uses GitHub's own fonts. Use clear section rhythm and a coherent badge system.
- Exactly three primary hero CTAs/badges: Official Website, product-relevant action (only when real), Created by PROCESS IN. Do not invent demo URLs or claims.
- Keep design language unified across products while retaining each product's real logo, proposition, and relevant product UI.

## Canonical README order

1. Centered **official logo** and premium product-specific hero illustration.
2. Coordinated branded badges and a concise positioning line / slogan.
3. **The problem and the product promise** — persuasive and grounded.
4. **How it works** — a 4–6 step workflow table, product-specific.
5. **Core capabilities** — informative two-column feature descriptions, 6–10 grounded modules or scope areas.
6. **Who it's for / use cases** — real audiences and value.
7. **Product experience** — visual or product screenshots only when verified, otherwise conceptual visuals explicitly labeled.
8. **MK-language presentation** — bilingual navigation and dedicated README.mk.md; main README must have a concise MK section or clear MK CTA.
9. **Product information** — domain, category, PROCESS IN developer link, public status with clear attribution, contact if verified.
10. Strong centered closing CTA and minimal confidentiality footer.

## Editorial rules

- No made-up statistics, testimonials, UI screenshots, integrations, plan prices, production readiness, or features.
- Separate current verified capabilities from roadmap or product concept, without flooding the page with disclaimers.
- Do not imply open-source licensing or expose proprietary code.
- Product READMEs should be **substantive** and visually rich, but never padded with generic filler.
- README.mk.md must be comparably substantive, not a short afterthought.
- Maintain common badges, heading hierarchy, tables, spacing and CTA conventions across all products.
- If the official logo is unavailable, do not claim visual parity with Validate; flag the missing asset.
- Review rendered GitHub README, including mobile width, image links, SVG rendering and contrast, before declaring complete.

**Source of truth:** This standard and the real product information, not copied generic prose.
## Discoverability and content depth

- Write substantial, product-specific documentation that answers genuine buyer and user questions: what it is, how it works, modules, industries, roles, workflows, integrations, benefits, terminology and common decision criteria.
- Favor semantic coverage and precise, natural explanations over repetition or keyword stuffing. More text alone does not guarantee search visibility.
- Include Macedonian and English terminology where relevant; do not leave English feature descriptions untranslated in the MK document.
- Describe real, owner-confirmed functionality confidently, but never invent metrics, endorsements, external integrations, prices or screenshots.
- Add accurate page titles, descriptive image alt text, relevant links and consistent product/category naming. GitHub repository metadata must match the content.
- Audit every existing showcase for completeness and visual parity, rather than applying the standard only to new repositories.
